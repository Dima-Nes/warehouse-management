## 1. Назначение и цели проекта

Современное складское хозяйство требует не просто фиксации факта нахождения товаров на полках, а комплексного контроля товарооборота в реальном времени с предотвращением ситуаций исчерпания запасов (**Stockout**) и заморозки оборотных средств в избыточных остатках (**Overstock**).

**Цели разработанного веб-приложения:**
1. **Оперативный учёт:** оприходование (приход), отпуск (расход), списание брака и внутренние перемещения номенклатуры.
2. **Контроль цепочки поставок:** ведение реестра поставщиков и заказов на закупку со статусной моделью (`Создан` &rarr; `Отправлен` &rarr; `Выполнен / Поступил` &rarr; `Отменён`).
3. **Предиктивная аналитика:** автоматический расчёт среднесуточного потребления (**ADU**), прогнозирование даты исчерпания товара и точки повторного заказа (**ROP**).
4. **Гарантия целостности данных:** защита от состояния гонки (Race Condition) и запрет списания товара в минус при одновременной работе сотрудников.
5. **Ролевая безопасность:** изоляция прав кладовщиков, менеджеров по закупкам и администраторов.

## 4. Подробный разбор подсистем и исходного кода

### 4.1. Авторизация и разграничение прав (`accounts`)

#### Зачем и как устроено:
Стандартная модель `User` в Django не разделяет служебные роли на уровне бизнес-логики предприятия. Для склада критично, чтобы **кладовщик** не имел права удалять контрагентов или видеть финансовые отчеты закупок, а **менеджер** имел оперативный доступ к заказам.

#### Ключевой код:
1. **Кастомная модель `CustomUser` (`accounts/models.py`):**
   ```python
   class CustomUser(AbstractUser):
       class Role(models.TextChoices):
           ADMIN = 'admin', 'Администратор'
           MANAGER = 'manager', 'Менеджер'
           WAREHOUSE_STAFF = 'warehouse_staff', 'Сотрудник склада'

       role = models.CharField(
           max_length=20,
           choices=Role.choices,
           default=Role.WAREHOUSE_STAFF,
           verbose_name='Роль в системе'
       )
   ```
   Модель расширяет `AbstractUser`, сохраняя интеграцию с Django Auth, хеширование паролей (PBKDF2/SHA256) и сессии. Добавлены удобные методы-свойства `is_admin`, `is_manager`, `is_warehouse_staff`.

2. **Декораторы контроля доступа (`accounts/decorators.py`):**
   Вместо дублирования условий `if request.user.role == ...` во всех контроллерах написан универсальный фабричный декоратор `@role_required(*roles)`:
   ```python
   def role_required(*roles):
       def decorator(view_func):
           @wraps(view_func)
           @login_required
           def _wrapped_view(request, *args, **kwargs):
               if request.user.role in roles or request.user.is_superuser:
                   return view_func(request, *args, **kwargs)
               messages.error(request, 'У вас недостаточно прав для выполнения этого действия.')
               return redirect('accounts:access_denied')
           return _wrapped_view
       return decorator
   ```
   И готовые алиасы: `@manager_or_admin_required`, `@warehouse_staff_required`, `@admin_required`.

3. **Безопасный логаут:**
   В Django 5+ и 6 выход из системы осуществляется строго через HTTP POST-запрос с проверкой CSRF-токена, исключая уязвимость CSRF Logout.

### 4.2. Контрагенты и управление закупками (`suppliers`)

#### Зачем и как устроено:
Подсистема организует работу отдела снабжения. Товар на складе привязан к основному поставщику. Закупка оформляется единым документом `PurchaseOrder` с детализацией позиций в `OrderItem`.

#### Ключевой код:
1. **Машина состояний заказа (`suppliers/models.py`):**
   Заказ не может переходить в произвольные статусы хаотично. Задана строгая матрица допустимых переходов:
   ```python
   class PurchaseOrder(models.Model):
       class Status(models.TextChoices):
           DRAFT     = 'draft',     'Создан'
           SENT      = 'sent',      'Отправлен поставщику'
           DELIVERED = 'delivered', 'Выполнен / Поступил'
           CANCELLED = 'cancelled', 'Отменён'

       STATUS_TRANSITIONS = {
           Status.DRAFT:     [Status.SENT, Status.CANCELLED],
           Status.SENT:      [Status.DELIVERED, Status.CANCELLED],
           Status.DELIVERED: [],   # Финальный статус
           Status.CANCELLED: [],   # Финальный статус
       }
   ```
   Метод `can_transition_to(new_status)` валидирует переход при попытке смены статуса.

2. **Динамический JavaScript-формсет позиций (`templates/suppliers/order_form.html`):**
   Для создания заказа с произвольным количеством строк позиций используется связка Django `inlineformset_factory` и клиентского JavaScript:
   - Кнопка «Добавить позицию» клонирует строку, инкрементирует `TOTAL_FORMS` в `management_form`.
   - Слушатели `input` пересчитывают сумму строки `Количество × Цена` и итоговую сумму заказа `orderTotal` на лету без перезагрузки страницы.

3. **Сквозная интеграция со складским учетом:**
   Когда менеджер переводит статус заказа в `DELIVERED`, в `suppliers/views.py` автоматически вызывается `inventory.services.post_purchase_order_delivery()`. По каждой строке формируется приходная складская проводка с автоматическим увеличением остатка товара!

### 4.3. Номенклатура, складские операции и сервис остатков (`inventory`)

#### Зачем и как устроено:
Сердце любой WMS — достоверность остатков. Если два сотрудника одновременно списывают товар, простая операция `product.quantity -= qty; product.save()` приведет к **Race Condition (состоянию гонки)** и потере данных. Мы решили эту проблему фундаментально на уровне архитектуры.

#### Ключевой код:
1. **Модель товара `Product` (`inventory/models.py`):**
   - Уникальный артикул `sku` с `db_index=True` для мгновенного поиска.
   - Единицы измерения через `TextChoices`: штуки (`pcs`), килограммы (`kg`), литры (`l`), метры (`m`), упаковки (`box`).
   - Базовая цена, остаток `quantity`, порог дефицита `min_quantity`.
   - Внешний ключ на поставщика `supplier = ForeignKey(Supplier, on_delete=SET_NULL, null=True, blank=True)`.
   - Вычисляемые свойства:
     - `is_low_stock` — `self.quantity <= self.min_quantity` (сигнал дефицита).
     - `is_out_of_stock` — `self.quantity == 0` (полное отсутствие).
     - `total_cost` — `Decimal(self.price) * Decimal(self.quantity)` (балансовая стоимость).

2. **Модель журнала проводок `StockMovement`:**
   Каждое изменение остатка фиксируется строкой с типом операции:
   - `in` — Приход (+);
   - `out` — Расход (−);
   - `writeoff` — Списание брака (−);
   - `transfer` — Внутреннее перемещение между зонами склада (−/+).

3. **Транзакционный сервис `inventory/services.py`:**
   ```python
   def register_movement(*, product, operation_type, quantity, user=None, document='', note='', purchase_order=None):
       if quantity <= 0:
           raise ValidationError('Количество должно быть больше нуля.')

       with transaction.atomic():
           # 1. Блокируем строку товара в PostgreSQL (SELECT FOR UPDATE)
           locked_product = Product.objects.select_for_update().get(pk=product.pk)

           if operation_type in StockMovement.INCREASE_TYPES:
               # Атомарное инкрементирование остатка на уровне СУБД
               Product.objects.filter(pk=locked_product.pk).update(
                   quantity=F('quantity') + quantity
               )
           elif operation_type in StockMovement.DECREASE_TYPES:
               # Строгая проверка наличия перед списанием
               if locked_product.quantity < quantity:
                   raise ValidationError(
                       f'Недостаточно товара на складе. В наличии: {locked_product.quantity}, запрошено: {quantity}.'
                   )
               # Атомарное декрементирование остатка на уровне СУБД
               Product.objects.filter(pk=locked_product.pk).update(
                   quantity=F('quantity') - quantity
               )

           # Фиксация в неизменяемом журнале аудита
           return StockMovement.objects.create(...)
   ```

#### Почему это надежно:
- **`select_for_update()`:** Захватывает эксклюзивную блокировку строки в PostgreSQL до окончания блока `with transaction.atomic()`. Любой параллельный запрос ожидает освобождения строки.
- **`F('quantity')`:** Выполняет вычисление непосредственно в SQL (`UPDATE inventory_product SET quantity = quantity - 5`), исключая рассинхронизацию значения в оперативной памяти Python.

### 4.4. Аналитический модуль и алгоритмы прогнозирования (`analytics`)

#### Зачем и как устроено:
Обычный склад констатирует факт: «товар закончился». Система с предиктивным модулем вычисляет динамику и заранее информирует: «при текущем темпе расхода этот кабель закончится через 4 дня; с учетом недели доставки оформите заказ поставщику прямо сегодня».

#### Математический аппарат (`analytics/services.py`):
1. **Среднесуточный расход (ADU — Average Daily Usage):**
   Анализирует фактические расходные проводки (`OUT` + `WRITEOFF`) за выбранный горизонт времени $N$ (14, 30, 60 или 90 дней):
   $$\text{ADU} = \frac{\sum_{i=1}^{M} \text{Quantity}_{\text{out}}}{N}$$

2. **Срок до исчерпания запаса (Stockout Days):**
   $$\text{Days Until Stockout} = \frac{\text{Current Quantity}}{\text{ADU}}$$

3. **Дата дефицита (Stockout Date):**
   $$\text{Date}_{\text{stockout}} = \text{Date}_{\text{today}} + \text{Days Until Stockout}$$

4. **Точка повторного заказа (ROP — Reorder Point):**
   Показывает, при каком остатке пора отправлять заявку поставщику с учетом времени доставки $L$ (Lead Time, по умолчанию 7 дней) и страхового остатка $S$ (`min_quantity`):
   $$\text{ROP} = (\text{ADU} \times L) + S$$

5. **Рекомендуемый объем дозаказа:**
   Рассчитывает партию пополнения для покрытия месячного спроса:
   $$\text{Reorder Qty} = \max\Bigl(0, (\text{ADU} \times 30 + S) - \text{Current Quantity}\Bigr)$$

#### Дополнительные сервисы модуля:
- **Генерация CSV-отчётов:** Функция `generate_inventory_csv()` выгружает реестр товаров с точкой с запятой `;` в качестве разделителя и префиксом байтов **UTF-8 BOM (`\ufeff`)**. Благодаря этому файл открывается в Microsoft Excel и LibreOffice Calc без повреждения кириллицы.
- **Email-уведомления о дефиците:** Функция `send_low_stock_notification()` сканирует позиции с `quantity <= min_quantity` и формирует аккуратную ASCII-таблицу дефицита со ссылкой на оформление заказа, отправляя её на служебный ящик администратора через `django.core.mail`.

## 5. Безопасность и защита от сбоев

1. **Защита от SQL-инъекций:** Все выборки используют ORM (`filter`, `Q`, `F`, `annotate`), параметры экранируются автоматически.
2. **Защита от CSRF:** Все формы используют тег `{% csrf_token %}`, логаут защищен методом POST.
3. **Защита от XSS:** Шаблонизатор Django по умолчанию экранирует HTML-спецсимволы.
4. **Контроль целостности связей (Referential Integrity):**
   - Товар ссылается на категорию с `on_delete=PROTECT` — категорию нельзя случайно удалить, пока в ней есть товары.
   - Поставщик привязан к товару с `on_delete=SET_NULL` — при удалении контрагента сам товар не пропадает.
   - Товар нельзя удалить из веб-интерфейса, если по нему уже зарегистрированы складские проводки.

## 8. Вопросы и ответы для защиты практики

**В: Почему для остатков используется сервисный слой, а не пересчёт прямо в представлениях (views)?**  
*О:* Складские операции могут инициироваться из разных мест: ручной приход кладовщиком, ручное списание, автоматический приход при закрытии заказа поставщика или фоновая интеграция. Сервис `register_movement()` обеспечивает единую точку входа с транзакционной целостностью и гарантирует, что бизнес-правила не будут нарушены ни в одном сценарии.

**В: Зачем нужен `select_for_update()`?**  
*О:* При одновременной работе нескольких сотрудников на складе возникает состояние гонки. Метод `select_for_update()` транслируется в SQL-конструкцию `SELECT ... FOR UPDATE`, которая блокирует строку в СУБД PostgreSQL на время транзакции, гарантируя, что ни один параллельный запрос не прочитает устаревший остаток до завершения текущей проводки.

**В: В чём отличие ADU от простого среднего расхода?**  
*О:* ADU (Average Daily Usage) рассчитывается строго по фактическим проводкам отпуска за скользящее окно (например, 30 дней), нивелируя случайные пиковые всплески и позволяя объективно рассчитать динамическую дату исчерпания товара и точку своевременного заказа (ROP).

**В: Почему выбран PostgreSQL, а не SQLite?**  
*О:* SQLite блокирует файл базы целиком при записи и не поддерживает блокировку отдельных строк `SELECT FOR UPDATE`. Для многопользовательской WMS-системы критически важна полноценная СУБД серверного уровня, поддерживающая конкурентный доступ и промышленный стандарт надежности ACID.
